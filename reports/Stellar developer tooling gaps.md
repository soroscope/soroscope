# StellarLens can own Soroban's live-state diagnostics gap

The best-supported opening for StellarLens is the "live-state diagnostics" layer that sits between the official Rust/CLI stack and the hosted indexers: provider-aware RPC routing, simulation-based failure explanation, and resource/TTL/footprint checks that run from TypeScript, a CLI and CI. Three product areas are crowded or poorly suited and should be avoided: general event indexers (Mercury, SubQuery, Goldsky, Obsrvr, Alchemy plus about 10 community repos), static analysis and formal verification (Scout, Certora Sunbeam, Komet, OpenZeppelin), and standalone WASM step-through debuggers (Runtime Verification's $150K SCF award, Erst, Prism). The evidence for demand is convergent but indirect. It comes from funded SCF proposals, GitHub issue ordering and official-doc admissions, because forum, Discord and survey data could not be retrieved. The strongest gaps are: no mature Stellar multi-RPC router or provider health probe; no tool that routes by retention window even though the RPC window is only about 7 days; no measured resource/fee regression tool for CI; no maintained TypeScript failed-transaction explainer; and no VS Code or language-server tooling found on GitHub. A TTL/archival monitor looks like a gap but is being attacked by about 8 brand-new repos. Most community repos are under three months old, have 0 to 15 stars, and look like Drips Wave output, so "no competitor" often means "no proven competitor." The recommended path is a four-phase roadmap: harden the SDK's routing and error layer (Phase 1), ship a CLI and a CI GitHub Action (Phase 2), add an MCP server and a probe-backed status dashboard (Phase 3), and treat the VS Code extension and TTL/upgrade tools as opportunistic later bets (Phase 4).

## Seven gaps hold up, ranked by evidence strength

Evidence quality varies sharply, so each gap is tagged. "Strong" means two or more independent signals (a funded proposal, official-doc admissions, or a high-ranked open issue). "Moderate" means one such signal plus absence in search. "Thin" means absence in GitHub search or repo descriptions only. The demand research could not read GitHub reaction counts and could not reach Discord, Reddit, the Stellar dev forum or any developer survey. Issue ranks below are therefore sort positions, not counts.

**1. Failed-transaction diagnosis and explanation (strong demand, crowded at the debugger end).** SCF #41 awarded **$150K** to Runtime Verification for a WASM-level debugger with a DAP server and VS Code/Cursor integration ([SCF submission](https://communityfund.stellar.org/submissions/recDYQJ63TqlNBacf)). The official debugging guide admits that `panic!` messages vanish in Wasm builds, leaving an opaque `WasmVm, InvalidAction`, and that budget failures require reading diagnostic events ([Stellar docs](https://developers.stellar.org/docs/learn/fundamentals/contract-development/errors-and-debugging/debugging-errors)). stellar-rpc #477 (return memory consumed in simulation) ranks second by reactions, and stellar-cli #1027 (replay command to introspect diagnostic events) is in the top ten ([stellar-rpc #477](https://github.com/stellar/stellar-rpc/issues/477), [stellar-cli #1027](https://github.com/stellar/stellar-cli/issues/1027)). Open CLI issues also complain about opaque host errors and lost diagnostic output ([#2772](https://github.com/stellar/stellar-cli/issues/2772), [#1089](https://github.com/stellar/stellar-cli/issues/1089)), and the SDK returns a raw error string, not a structured error code, so Colibri had to build a parser ([JSR](https://jsr.io/@colibri/core@0.23.0/doc/~/ParsedSimulationContractError)). The step-through end is claimed by Erst (pre-alpha, build from source), Prism (unverified end to end) and the funded RV project. The unfilled niche is a lighter, npm-installable explainer: hash or XDR in, decoded host error, diagnostic-event tree, contract error enum name and suggested fix out. StellarLens already does part of this.

**2. RPC reliability, provider health and retention-aware routing (moderate, least contested).** The RPC keeps about **120,960 ledgers (about 7 days)** and `getHealth` reports `oldestLedger`. Only `getLedgers` can read deeper, through an optional data lake. The docs describe no subscription API and publish no rate limits ([getEvents docs](https://developers.stellar.org/docs/data/apis/rpc/api-reference/methods/getEvents), [SDF infinite scroll post](https://stellar.org/blog/developers/rpc-now-with-infinite-scroll)). The SDF provider table lists "archive" per provider but gives no latency, uptime, retention or rate-limit data ([providers](https://developers.stellar.org/docs/data/apis/rpc/providers)). The closest tools are OpenZeppelin Monitor, a Rust service whose rotation is mainly rate-limit driven ([docs](https://docs.openzeppelin.com/monitor/1.0.x/rpc)), and a one-star, weeks-old TS ping CLI. No public multi-provider status or latency dashboard exists; only third-party aggregators of SDF components ([Pingoru](https://pingoru.io/providers/stellar/incidents/21071)). Whether js-stellar-sdk's `rpc.Server` has any failover was not verified; it takes a single URL as far as its API shape suggests.

**3. Resource, fee and footprint legibility with CI regression checks (moderate).** Simulation returns raw `cpuInsns`/`memBytes` JSON, and a sorocrew/studio issue asks for a visual breakdown ([issue 2](https://github.com/sorocrew/studio/issues/2)). The searches found no tool measuring budget regression; Tollcraft's linter is static only, and the profilers found have 0 stars and are Rust ([Soroban-Profiler](https://github.com/CollinsKRO/Soroban-Profiler)). The research found one GitHub Action that mentions a budget estimator, as part of a fuzz toolkit ([Soroban-Fuzzer](https://github.com/Soroban-Static-Analysis-Fuzzing-Toolkit/Soroban-Fuzzer)). This rests on search absence, and two GitHub-search queries on mutation testing and Actions were rate-limited.

**4. TTL and archival (strong need, crowded).** Veridise names archival as a bug source ([Veridise](https://veridise.com/blog/learn-blockchain/how-is-stellar-funding-smart-contract-security-at-scale/)), Scout's 23 detectors include none for TTL ([Scout docs](https://coinfabrik.github.io/scout-soroban/docs/detectors)), and stellar-cli #790 on bump/restore ergonomics is second by reactions ([#790](https://github.com/stellar/stellar-cli/issues/790)). A static linter cannot see live TTLs, so an RPC-reading tool fits. But roughly eight 2026 repos already target this (see the table), so the niche is claimed even if no entrant is proven.

**5. Typed bindings, SDK churn and migration (strong, but mostly SDF's job).** stellar-cli #2758 (opened 2026-09-26) reports that `bindings typescript` was deprecated in CLI 28.1.0 before its replacement plugin shipped in SDK 17.1.0, and the plugin ignores CLI config and rejects `--network local`; js-stellar-sdk #1755 on plugin parity is top five by reactions ([#2758](https://github.com/stellar/stellar-cli/issues/2758), [#1755](https://github.com/stellar/js-stellar-sdk/issues/1755)). Search found no Go, Kotlin or Swift contract-binding generator, but that is absence only. This is a compatibility-linting opportunity at most, because the owners of the fix are upstream.

**6. Fork testing, source verification, smart accounts (real, but heavy or owned elsewhere).** A persistent fork node that JS tools can target does not exist; soroban-fork is Rust in-process ([docs.rs](https://docs.rs/soroban-fork)). Source verification is fragmented between SEP-55 (Draft since 2025-03, trusts GitHub), SEP-58 and small verifiers, and SCF #44 is funded work ([SEP-55](https://github.com/stellar/stellar-protocol/blob/master/ecosystem/sep-0055.md), [SCF #44](https://communityfund.stellar.org/dashboard/submissions/receWOpMjj7FxAydj)). Smart-account CLI support (stellar-cli #2762) is in the top ten, and Protocol 27's CAP-71 auth delegation raises the need for auth-entry inspection, though P27's mainnet outcome was unconfirmed ([#2762](https://github.com/stellar/stellar-cli/issues/2762), [Nansen](https://nansen.ai/post/stellar-q2-2026-report)).

**7. Ecosystem utilities: SEP-1 linting, trustline auditing, SAC/SEP-41 inspection, bulk builders, tax export (thin).** Existing stellar.toml checkers are 0 to 6 stars or stale, no trustline auditor exists beyond hobby apps (0 to 4 stars), the official claimable-balance utils repo is archived, and the one tax exporter is stale ([stellar-toml-lint](https://github.com/anchor-tools/stellar-toml-lint), [ledgers-tax](https://github.com/stellar-expert/ledgers-tax)). The evidence is repo-description-level only, and no demand signal was gathered. These are TypeScript-friendly but mostly off-mission for a read-only diagnostic SDK, and the bulk builders require signing and submitting, which StellarLens does not do.

## Where StellarLens differs from the field and what is still unproven

StellarLens ships latency-ranked fallback in an in-process SDK, simulation pre-flight and human-readable XDR error decoding, and it does not sign or submit ([README](/home/ezedikeevan/Desktop/blockchain/stellar/stellarlens/README.md)). Against the field, the real differentiators are in-process embedding (OZ Monitor is a separate service, stellar-rpc-ping a one-shot CLI) and latency ranking rather than 429-only rotation. Error decoding is partly served by Colibri's `parseFailedSimulationResponse` and by Prism and tiny decoders, none above 9 stars, so decoding alone is not a moat; the moat is decoding integrated with routing and simulation. Not yet differentiated: ledger-lag awareness, `oldestLedger`-aware per-method routing, `Retry-After` handling, hedged requests, circuit breakers and persisted health history. Routing by retention coverage is the notable open niche, because the SDF table lists "archive" per provider and no tool consumes it.

Two strategic constraints follow from the evidence. First, the read-only stance is an asset for trust and for MCP/CI use, so the roadmap keeps it. Second, the ecosystem churns quickly: Horizon is "nearing end-of-life" in favor of RPC ([Stellar APIs](https://developers.stellar.org/docs/data/apis)), protocols 25 to 27 added ZK primitives, frozen ledger keys (CAP-77), TTL v2 and auth delegation ([P26 guide](https://stellar.org/blog/foundation-news/stellar-yardstick-protocol-26-upgrade-guide)), and the soroban-rpc to stellar-rpc rename deprecated old packages. Any decoder or error catalog needs a versioned, test-backed update process. The error catalog should be exported as language-neutral JSON, which would also serve the stale Ruby and .NET SDK ecosystems.

## A four-phase roadmap built on what StellarLens already does

Effort estimates below are my judgment for one experienced TypeScript developer, not figures from the research. "Crowded" flags come from the catalog above.

**Phase 1: Harden the core SDK (about 3 to 5 weeks; highest rationale).** Add provider-aware routing signals: ledger-lag exclusion using `getLatestLedger`, `getHealth.oldestLedger` capture, `Retry-After`/429 backoff, per-method routing so `getLedgers` and old `getEvents` go only to providers whose window covers the request, circuit breakers, optional hedged requests, and -32001 timeout handling. Extend the simulation layer to classify outcomes (restore-required, auth, resource-limit, contract error, host error) and return structured results, since the SDK only returns a raw error string. Decode diagnostic events into an ordered tree, resolve contract error enum names from the contract spec, and ship a versioned JSON error catalog. Rationale: all of this builds on existing code, has no proven competitor, and every later product reuses it. Avoid building a router that needs a hosted backend at this stage.

**Phase 2: CLI and CI GitHub Action (about 3 to 4 weeks).** The CLI exposes `explain <hash|xdr>`, `simulate`, `probe` (latency, lag, retention, archive success across providers), and `budget` (cpu/mem/footprint/fee for a transaction fixture). The Action runs `budget` against baseline fixtures on testnet or a pinned snapshot and fails a PR on regressions, with SARIF or Markdown summary output. Rationale: the resource-regression gap rests on only moderate evidence, but it is a rare place where a read-only tool wins on its own terms, and CI is where Scout's own Action went stale (17 months without a commit). Avoid a static-linter Action; that space has about ten young entrants.

**Phase 3: MCP server and probe-backed status dashboard (about 3 to 5 weeks for MCP, 4 to 6 for the dashboard).** The MCP server exposes read-only tools (`decode_xdr`, `simulate`, `explain_failure`, `probe_providers`, `ttl_status`). The only active Stellar MCP found is stellar-raven (docs and ecosystem gateway, 9 stars) and the only XDR-specific one is mcp-stellar-xdr (1 to 2 stars), so a simulation-and-diagnosis MCP is differentiated, though agent tooling is a fast-moving space. The dashboard publishes probe results per provider: p50/p99 latency, error and 429 rates, ledger lag, `oldestLedger`, archive `getLedgers` success. No public equivalent was found. A hosted probe network has unassessed cost and feasibility, so start with a scheduled GitHub-Actions-fed static page. Avoid contract-event alerting here (OZ Monitor, SoroBeacon and Alchemy cover it); provider-health alerting has no competitor found.

**Phase 4: Opportunistic bets (each 2 to 6 weeks, decide with evidence).** A TTL doctor that reads live ledger entries and footprints from simulations and flags near-expiry entries fits the RPC-aware design, but only if the crowded field has not converged by then; a read-only variant that reports and never extends TTL stays within scope. A VS Code extension wrapping `explain` and `budget` is attractive because GitHub search found no Soroban extension or language server, but the marketplace was not checked, and RV's funded debugger will target the same editors; keep the scope to inline decoding and cost hints. A gap-aware event follower (cursor, dedup by event id, detection of "start ledger below oldest", pluggable backfill) is a thin library rather than an indexer. A differential-simulation mode that runs the same transaction across providers and ledgers and diffs results leverages the routing layer, and the research found no tool that does it. An auth-entry inspector is timely given CAP-71 and smart accounts.

**What to avoid.** Do not build a general indexer or explorer (Mercury, SubQuery, Goldsky, Obsrvr, Alchemy, Stellar Expert and about 10 community repos). Do not build static analysis, fuzzing or formal verification (Scout, Sunbeam, Komet, OpenZeppelin, plus a flood of near-duplicate linters). Do not build a WASM step-through debugger (RV's $150K award, Erst, Prism). Do not build source-verification infrastructure while SEP-55 versus SEP-58 is unsettled; consume a verifier's result if one wins. Do not build signing, wallet, bulk-payment or tax tools, which conflict with the read-only identity. Do not build bindings generators; the churn is SDF's to fix. Funding note: SCF has a developer-tooling category, so a Build-track application around Phase 1 to 3 is plausible, but no 2026 RFP list for tooling was found ([SCF awards](https://communityfund.stellar.org/awards)).

## Caveats and unverified items

The evidence base has clear limits. No hands-on testing of any community tool was done, so claims about Erst, Prism, soroban-fork and the 2026 linters come from READMEs or one-line GitHub descriptions. Many 2026 repos look like Drips Wave output, with near-zero stars and high fork counts, so their existence signals activity rather than demand or quality, and Wave PR counts measure maintainer backlog, not developer need ([Drips docs](https://docs.drips.network/wave)). GitHub search was rate-limited partway, ranks by stars and misses very obscure repos, so "no tool found" claims (mutation testing, wasm-size optimizers, VS Code extensions, Go/Kotlin/Swift binding generators, OpenTelemetry tracing for Soroban, fee-bump tooling) are weak evidence. No Discord, forum, Reddit, Stack Overflow or developer-survey data was retrieved, GitHub reaction counts were hidden, and the demand ranking is therefore convergence-based, not counted.

Specific facts remain unconfirmed. Sunbeam's license and repo location, Komet's current host-function coverage, and the status of Almanax, DYET, Solarkraft, Extractor, Decentrio and Sorobanhooks are unknown. SEP-58's text and `stellar contract optimize` were not read. Protocol 27's mainnet outcome and Launchtube's status were not confirmed. SCF #40 and the VS Code extension proposal rest on search summaries, not fetched pages. Per-provider rate limits, real retention, uptime and pricing are not published, and whether js-stellar-sdk offers any failover is unverified. The marketplace, npm and crates.io were not searched, and no adoption (download) figures were collected. Several guessed repo paths returned 404, including an official Aquarius SDK, a Reflector client and a scaffold-stellar repo, so those may exist under other names. The Stellar Expert, StellarChain, Lumenscan, DefiLlama and Dune-style analytics comparisons were not covered. Dates and star counts are a 2026-10-08 snapshot and age quickly in a field where most competitors are weeks old.

## Conclusion

The research changes the framing of the question: Stellar's problem is not a shortage of repos but a shortage of trusted, maintained, integrated ones. The official stack is deep but Rust and CLI shaped, and the community layer is a crowd of unproven micro-projects. That makes continuity and trust the scarce assets. A small tool that stays maintained, tracks protocol changes and ships its decoding, routing and simulation as one coherent TypeScript surface can win without out-building anyone on features.

The corollary is discipline. The most defensible StellarLens position is the one competitors cannot easily copy from a repo description: operational knowledge of how real RPC providers behave (latency, lag, retention, rate limits) fed back into routing and into failure explanations. Everything on the roadmap either collects that knowledge (probe, dashboard), applies it (routing, CI budget checks), or exposes it to people and agents (CLI, MCP, editor). Demand for the rest of the catalog's gaps should be validated with Discord and forum research and with the first users of Phase 1 before any Phase 4 item is committed.
